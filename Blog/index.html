Introduction

Authentication and authorization are important parts of modern web applications. When you log in to an application, the server needs a reliable way to recognize you on later requests.

One common approach is token-based authentication. After a successful login, the server issues a token. The client presents that token when it requests protected data.

In this blog, you will learn what tokens and JWTs are, how access and refresh tokens differ, and how to build a small working example with Node.js, Express, and JSON Web Token.

1. What is a Token?

A token is a piece of data that a server issues to a client and later checks to authenticate a request or authorize an action. You can think of it as a temporary digital pass.

  1. The user enters their login credentials.
  2. The server verifies those credentials.
  3. If they are correct, the server issues a token.
  4. The client sends the token with requests to protected endpoints.
  5. The server validates the token before returning protected information.

A token is not the user's password. It is a credential that must be protected because someone who steals a valid token may be able to use it.

2. What is JWT?

JWT stands for JSON Web Token. It is a standard format (RFC 7519) for representing claims as a JSON object that can be digitally signed and verified.

A signed JWT commonly has three Base64URL-encoded parts separated by dots:

HeaderToken type and signing algorithm
PayloadClaims such as user ID and role
SignatureHelps verify integrity
xxxxx.yyyyy.zzzzz

Header example

{
  "alg": "HS256",
  "typ": "JWT"
}

Payload example

{
  "userId": "123",
  "role": "user"
}
Important: A normal signed JWT is encoded, not encrypted. Anyone who obtains it can usually decode and read its payload. Do not put passwords, secrets, or sensitive personal data in a JWT.

3. What is an Access Token?

An Access Token is a credential that the client sends to access protected API endpoints. The server validates it and, if it is valid and authorized, allows the request.

For example, a client might send:

Authorization: Bearer YOUR_ACCESS_TOKEN

Access tokens are generally short-lived. A common learning example is 15 minutes, although the correct lifetime depends on the application's security requirements.

4. What is a Refresh Token?

A Refresh Token is a longer-lived credential used to obtain a new access token after the current access token expires. It lets the user continue a session without entering their password each time.

  1. The access token expires.
  2. The client sends its refresh token to a refresh endpoint.
  3. The server verifies the refresh token and checks whether it is still active.
  4. If valid, the server issues a new access token. A robust design also rotates the refresh token.

A refresh token is especially sensitive. In browser applications, an HttpOnly, Secure cookie is a common storage choice, with appropriate SameSite and CSRF protections.

5. Access Token vs Refresh Token

FeatureAccess TokenRefresh Token
PurposeAccess protected APIsObtain a new access token
LifetimeShort-livedLonger-lived
Example lifetime15 minutes7 days
Sent toProtected API endpointsRefresh endpoint only
Typical browser handlingKeep in memory where practicalHttpOnly, Secure cookie
Security concernLimit exposure with a short lifetimeProtect, rotate, and revoke it

The lifetimes above are illustrative examples, not universal rules.

6. How Access Token and Refresh Token Work Together

Access Tokens and Refresh Tokens work together to keep users logged in while protecting access to private APIs.

1
User Login

The user enters their email address and password in the application.

2
Server Verification

The server checks the submitted credentials against the user's account.

3
Generate Tokens

If the credentials are valid, the server creates an Access Token (for example, 15 minutes) and a Refresh Token (for example, 7 days).

4
Access a Protected API

The client sends the Access Token with API requests. The server verifies it before returning protected data.

5
Access Token Expires

When the Access Token expires, the server rejects the protected request. The user does not need to enter their password again.

6
Refresh Token Request

The client sends its Refresh Token to the refresh endpoint. The server validates it and checks that it has not been revoked or reused.

7
Generate a New Access Token

If the Refresh Token is valid, the server issues a new Access Token. A secure system may also rotate the Refresh Token.

Result: The user can continue using the application without logging in again, as long as the Refresh Token remains valid.

7. Project Setup

Now let's create a small Express server that demonstrates login, a protected route, refresh, and logout.

Install dependencies

mkdir jwt-auth
cd jwt-auth
npm init -y
npm install express jsonwebtoken cookie-parser dotenv cors
npm install --save-dev nodemon

In package.json, set the module type and development script:

{
  "type": "module",
  "scripts": {
    "dev": "nodemon server.js"
  }
}

Create a .env file

PORT=3000
ACCESS_TOKEN_SECRET=replace_with_a_long_random_secret
REFRESH_TOKEN_SECRET=use_a_different_long_random_secret
CLIENT_URL=http://localhost:5173
Use different, high-entropy secrets for access and refresh tokens. Keep .env out of Git and never expose these secrets in frontend code.

8. Complete Working Backend Code

Create server.js. This learning demo uses one hard-coded user and an in-memory refresh-token store, so you can test the flow without MongoDB.

Demo login: test@gmail.com / 123456

import express from "express";
import jwt from "jsonwebtoken";
import cookieParser from "cookie-parser";
import cors from "cors";
import dotenv from "dotenv";
import { randomUUID } from "node:crypto";

dotenv.config();

const app = express();

app.use(express.json());
app.use(cookieParser());

app.use(cors({
  origin: process.env.CLIENT_URL,
  credentials: true
}));

// Demo user only. Replace this with a database lookup.
const user = {
  id: "123",
  email: "test@gmail.com",
  password: "123456",
  role: "user"
};

// Demo-only storage. Use persistent database storage in production.
const refreshTokens = new Map();

const createAccessToken = (user) => {
  return jwt.sign(
    { userId: user.id, role: user.role },
    process.env.ACCESS_TOKEN_SECRET,
    { expiresIn: "15m" }
  );
};

const createRefreshToken = (user) => {
  return jwt.sign(
    { userId: user.id },
    process.env.REFRESH_TOKEN_SECRET,
    {
      expiresIn: "7d",
      jwtid: randomUUID()
    }
  );
};

const cookieOptions = {
  httpOnly: true,
  secure: process.env.NODE_ENV === "production",
  sameSite: "lax",
  maxAge: 7 * 24 * 60 * 60 * 1000,
  path: "/api/auth"
};

// LOGIN
app.post("/api/auth/login", (req, res) => {
  const { email, password } = req.body;

  if (email !== user.email || password !== user.password) {
    return res.status(401).json({
      message: "Invalid email or password"
    });
  }

  const accessToken = createAccessToken(user);
  const refreshToken = createRefreshToken(user);

  refreshTokens.set(user.id, refreshToken);
  res.cookie("refreshToken", refreshToken, cookieOptions);

  return res.json({
    message: "Login successful",
    accessToken
  });
});

// ACCESS TOKEN MIDDLEWARE
const authenticate = (req, res, next) => {
  const authHeader = req.headers.authorization;

  if (!authHeader?.startsWith("Bearer ")) {
    return res.status(401).json({
      message: "Access token required"
    });
  }

  const token = authHeader.split(" ")[1];

  try {
    req.user = jwt.verify(
      token,
      process.env.ACCESS_TOKEN_SECRET
    );
    next();
  } catch (error) {
    return res.status(401).json({
      message: "Invalid or expired access token"
    });
  }
};

// PROTECTED ROUTE
app.get("/api/user/profile", authenticate, (req, res) => {
  return res.json({
    message: "Protected profile accessed successfully",
    user: req.user
  });
});

// REFRESH ACCESS TOKEN
app.post("/api/auth/refresh", (req, res) => {
  const token = req.cookies.refreshToken;

  if (!token) {
    return res.status(401).json({
      message: "Refresh token missing"
    });
  }

  try {
    const decoded = jwt.verify(
      token,
      process.env.REFRESH_TOKEN_SECRET
    );

    // Check that this is the currently active refresh token.
    if (refreshTokens.get(decoded.userId) !== token) {
      return res.status(403).json({
        message: "Refresh token revoked or reused"
      });
    }

    const newAccessToken = createAccessToken(user);
    const newRefreshToken = createRefreshToken(user);

    // Rotate the refresh token.
    refreshTokens.set(user.id, newRefreshToken);
    res.cookie("refreshToken", newRefreshToken, cookieOptions);

    return res.json({
      message: "Token refreshed successfully",
      accessToken: newAccessToken
    });
  } catch (error) {
    return res.status(403).json({
      message: "Invalid or expired refresh token"
    });
  }
});

// LOGOUT
app.post("/api/auth/logout", (req, res) => {
  const token = req.cookies.refreshToken;

  if (token) {
    try {
      const decoded = jwt.verify(
        token,
        process.env.REFRESH_TOKEN_SECRET
      );

      if (refreshTokens.get(decoded.userId) === token) {
        refreshTokens.delete(decoded.userId);
      }
    } catch (error) {
      // Cookie may already be expired or invalid.
    }
  }

  res.clearCookie("refreshToken", {
    httpOnly: true,
    secure: process.env.NODE_ENV === "production",
    sameSite: "lax",
    path: "/api/auth"
  });

  return res.json({
    message: "Logged out successfully"
  });
});

const PORT = process.env.PORT || 3000;

app.listen(PORT, () => {
  console.log(\`Server running on port \${PORT}\`);
});

Start the server

npm run dev

You should see: Server running on port 3000.

Demo limitations: The hard-coded password is plain text, the refresh-token Map is lost when the server restarts, and it supports only one active refresh token per demo user. For production, use a database, hash passwords with bcrypt or Argon2, store hashed refresh tokens per session, and implement appropriate CSRF protection.

9. Test the APIs Using Postman

A. Login

POST http://localhost:3000/api/auth/login

Choose Body → raw → JSON:

{
  "email": "test@gmail.com",
  "password": "123456"
}

The response contains an access token. Postman should also save the refresh-token cookie for localhost.

B. Access the protected profile

GET http://localhost:3000/api/user/profile

Set this header using the access token returned by login:

Authorization: Bearer YOUR_ACCESS_TOKEN

C. Refresh the access token

POST http://localhost:3000/api/auth/refresh

No body is required. Send the refresh-token cookie received during login. The response returns a new access token and rotates the refresh cookie.

D. Logout

POST http://localhost:3000/api/auth/logout

The server invalidates the active demo refresh token and clears the cookie. The already-issued access token can remain valid until it expires; production systems may add access-token revocation when immediate logout is required.

10. React Integration Using Axios

Install Axios in your React application:

npm install axios

Create api.js. This simple example keeps the access token in memory and relies on the browser to send the HttpOnly refresh cookie.

import axios from "axios";

const api = axios.create({
  baseURL: "http://localhost:3000/api",
  withCredentials: true
});

let accessToken = null;

export const setAccessToken = (token) => {
  accessToken = token;
};

// Attach access token to API requests.
api.interceptors.request.use((config) => {
  if (accessToken) {
    config.headers.Authorization = \`Bearer \${accessToken}\`;
  }

  return config;
});

// Refresh once after an access-token failure.
api.interceptors.response.use(
  (response) => response,
  async (error) => {
    const originalRequest = error.config;

    if (
      error.response?.status === 401 &&
      originalRequest &&
      !originalRequest._retry &&
      !originalRequest.url?.includes("/auth/")
    ) {
      originalRequest._retry = true;

      try {
        const response = await api.post("/auth/refresh");
        const newToken = response.data.accessToken;

        setAccessToken(newToken);
        originalRequest.headers.Authorization =
          \`Bearer \${newToken}\`;

        return api(originalRequest);
      } catch (refreshError) {
        setAccessToken(null);
        return Promise.reject(refreshError);
      }
    }

    return Promise.reject(error);
  }
);

export default api;

Login example

import api, { setAccessToken } from "./api";

async function login() {
  const response = await api.post("/auth/login", {
    email: "test@gmail.com",
    password: "123456"
  });

  setAccessToken(response.data.accessToken);
}

Call a protected API

async function getProfile() {
  const response = await api.get("/user/profile");
  console.log(response.data);
}
React note: In-memory access tokens disappear on a page reload. A real app should restore the session by calling the refresh endpoint during app initialization. Also handle simultaneous 401 responses with a single shared refresh operation, and configure CSRF protection for cookie-based refresh requests.

11. Important Security Practices

  • Never store user passwords in plain text. Use bcrypt or Argon2 with appropriate parameters.
  • Never expose JWT signing secrets in frontend code or public repositories.
  • Keep access tokens short-lived.
  • Protect refresh tokens, commonly with HttpOnly and Secure cookies in browser applications.
  • Use HTTPS in production.
  • Rotate refresh tokens and detect reuse of old tokens.
  • Store hashed refresh tokens in persistent server-side storage and support revocation.
  • Use appropriate CSRF defenses when authentication relies on cookies.
  • Validate token claims and enforce authorization on every protected endpoint.

12. Conclusion

Token-based authentication is widely used to protect APIs and manage user sessions in modern web applications.

  • Token: A credential used to authenticate or authorize requests.
  • JWT: A standard format for carrying signed claims.
  • Access Token: Used to access protected APIs.
  • Refresh Token: Used to obtain a new access token without asking the user to log in again.

Practice the backend flow with Postman first. Then connect it to React and, after understanding the basics, replace the demo user and in-memory store with MongoDB and persistent session management.
